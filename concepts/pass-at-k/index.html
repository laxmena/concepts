pass@k

pass@k scores a code model by letting it try a problem k times and asking whether any try passes the tests. HumanEval and the Codex paper made it the standard code metric.

  • A code eval runs the model’s program against unit tests, so a try either passes or fails.
  • pass@k asks whether any of k tries passes, so more tries can only help.
  • It is estimated from n samples with a count, not by running exactly k tries once.
  • The reverse question, do all k tries pass, shows how reliable the model is.

Show the formula

Generate n samples per problem, count the c that pass the tests, then average this over problems.

pass@k = 1 − C(n − c, k) / C(n, k) all k pass = C(c, k) / C(n, k)

C(a, b) is the number of ways to choose b items from a. The fraction is the chance that k samples drawn without replacement are all failures, so one minus it is the chance of at least one pass. When fewer than k samples fail, pass@k is 1. The paper uses n = 200 and k up to 100, and computes the fraction as a running product so the numbers stay small.

Where you meet it

A team says its code model “solves 70% of problems”. The first question to ask is how many tries it got.

  • The Codex paper introduced HumanEval, 164 hand-written problems with an average of 7.7 unit tests each, and reports pass@k from n = 200 samples. Its abstract says the model solves 70.2% of problems with 100 samples per problem.
  • SWE-bench scores a model by whether the tests pass after it edits a real code base, across 2,294 tasks from GitHub issues.
  • τ-bench borrows the idea and flips it. Its pass^k counts a task only when all k runs succeed, which suits a customer-service agent that must work every time.

Check yourself

n = 10 samples, c = 3 pass. What is pass@2?

The chance that two samples drawn without replacement are both failures is C(7,2) / C(10,2) = 21/45. So pass@2 = 1 − 21/45 = 24/45, about 0.53. The naive shortcut gives 1 − 0.7² = 0.51.

A model solves one problem every time and never solves another. What is its average pass@5 over the two?

0.5. Each problem gets its own estimate (1 and 0) and the estimates are averaged. More tries cannot help a problem the model never solves.

Why not run exactly k tries once and report whether any passed?

That is one noisy draw. The paper notes this way of computing pass@k can have high variance. Drawing n ≥ k samples and counting uses all of them and gives an unbiased estimate with less noise.
