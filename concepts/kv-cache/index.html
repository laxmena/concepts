KV cache

The memory a language model keeps while it writes, so it does not reread everything for each new token.

  • A model writes one token at a time, and each new token looks at every token before it.
  • The keys and values of earlier tokens never change, so the model can save them.
  • That saved pile is the KV cache. It makes the total work grow in a straight line instead of with the square.
  • The price is memory, and it grows with every token and every person at once.

What just happened

  1. To write token number t, attention needs a key and a value from every earlier token, in every layer. A token’s key and value depend only on the tokens before it, so once computed they never change.
  2. Without a cache the model runs all t earlier tokens through itself again at every step. After tokens that adds up to token passes. With a cache it is , about less.
  3. With a cache, each step runs only the new token. It writes its own key and value into the cache and reads the saved ones. Attention still reads every saved entry, so a step gets a little slower as the text grows. The expensive rerun is gone.
  4. The cache holds a key and a value for every token, layer and head. For this model that is 2 × layers × heads × numbers × bytes = bytes, about , for every token. At tokens that is .
The numbers behind it

The model here is shaped like Llama 3 8B: 32 layers, 8 key/value heads shared by 32 query heads (grouped-query attention), 128 numbers per head, 16-bit numbers. Giving every head its own keys and values, as the original transformer did, would be 32 KV heads and a token, four times as much.

The page leaves out the prompt. A real server runs the whole prompt through the model in one parallel pass, fills the cache, and then writes one token per step. Queries are never cached, because each query is used once, at its own step.

Where you meet it

Every serving system for a transformer keeps a KV cache. The cache is why the first token of a reply takes a moment (the prompt is processed) and the rest stream quickly, and why a longer conversation costs more memory to serve.

  • Grouped-query attention exists to shrink the cache: several query heads share one key and value head.
  • vLLM’s PagedAttention stores the cache in small blocks, like pages of virtual memory, so little of it is wasted on unused space.

Where it breaks

The cache is per person and per token. A GPU serving many people at once runs out of memory long before it runs out of arithmetic. Drag the people and the length up, then switch the number of KV heads.

With tokens each, one person takes of cache. On a GPU with of weights, about people fit with 8 KV heads and with 32. Real servers also need room for other working memory, so the true numbers are lower.

Check yourself

Why does the cache hold keys and values but not queries?

A query is used once, by the token that makes it, to look at the earlier tokens. No later token needs an old query. Every later token does need the old keys and values, so those are kept.

With a cache, is attention now free?

No. Each step still reads every saved key and value, so the cost of a step grows with the length. What the cache removes is running the earlier tokens through the whole model again.

Twice the people, or twice the tokens each. Which one needs more cache?

Neither. The cache is people × tokens × bytes per token, so both double it. Only the shape of the model changes the bytes per token.
