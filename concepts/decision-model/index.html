Decision models (System One)

Small models that choose among options instead of writing text, used inside AI agents to route, check and gate actions.

  • An agent makes many small choices: which tool, whether an action is safe, which path to take.
  • A decision model takes the situation and a list of options and returns one probability per option, in a single pass.
  • The answer is a number code can act on, not a sentence to parse.
  • The name System One borrows the fast, automatic kind of thinking from Kahneman’s System 1 and System 2.

What just happened

  1. The model is given the situation, here a request, and a typed question: which of tools? The options are a fixed list that the developer writes.
  2. It gives every option a score in one forward pass, then a softmax turns the scores into probabilities that add up to 100%. For “What is 17% of 240?” the first option, Math, gets .
  3. Code reads the probability directly. There is no sentence to parse, and the answer is always one of the options on the list.
  4. An LLM that answers in words writes something like “I would use the calculator, since the question is arithmetic.” That is tokens, one pass through the model each, and then code has to work out which tool it meant.
What the models are, and a fair warning

Jev from TypeSafe AI was the first named System One model. Others now exist, including Laya, Strands Decider from AWS and decision models from several large companies. They take typed questions: choose one option, a yes or no probability, or a score on a scale. How they read the answer out differs: some read option probabilities from an ordinary language model’s next-token scores, others add a dedicated output head that scores each option.

A community audit listed alongside these models finds that the typed readout alone gives no accuracy advantage over reading label probabilities from a comparable model. The gains it does find are in speed and cost, plus the fact that these models are trained to give probabilities that mean something. The scores on this page are made up, so it shows the shape of the answer, not how accurate any model is.

Where you meet it

  • Routing: pick the tool, the agent or the model that should handle a request.
  • Gates: before an agent runs a tool, ask whether the arguments look right and whether to proceed, ask the user, or stop. AWS shows this with Strands Decider, a small model that runs locally.
  • Cascades: let the cheap decision model handle what it is sure about, and send the rest to a large LLM.

Check yourself

A decision model returns 67% for a tool. Does that mean it is right two times in three?

Only if the model is calibrated. A softmax always produces numbers that add to 100%, whether or not the model has earned them. Calibration is checked by counting how often the model is right when it says 67%, over many decisions.

Why not just ask an LLM to pick, and read the probability of each option’s first token?

You can, and some decision models are built exactly that way. It also takes one pass. What a purpose-built model adds is training for probabilities that mean something, a smaller and cheaper model, and an interface made for typed questions. The audit above found the readout alone gives no accuracy gain.

Which decisions should not be left to a model like this?

Ones that need knowledge the model does not have or that depend on writing. The Jev documentation says it only knows the state it is given and cannot look things up. For costly actions, use a high confidence bar and send the rest to a person or a stronger model.
